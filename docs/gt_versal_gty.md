# Versal GTY wrapper

One to four channels of one Versal GTY (GTYE5) quad as independent `omac_10g` lanes at
10.3125 Gb/s (10GBASE-R), in the transceiver's 64B/66B **asynchronous gearbox** mode:
`omac_gt_versal_gty_quad`. It is the Versal counterpart of the UltraScale+ quad wrappers
([](gt_usp_gth.md#independent-lanes-omac_gt_usp_gth_quad-omac_gt_usp_gty_quad)) with the same
parameters, ports and per-lane behaviour, so a design takes either with a generate branch on the
transceiver type. Built from AMD's free `gt_quad_base` IP (no license key), generated by
`gt/omac_gt_versal_gty/gen_gt.tcl`, not checked in. **Maturity (v0.2.0-dev):** simulated with
the transceiver models (two lanes crossed, link-up, frames both ways, bit order checked on the
serial line), implemented in a complete Versal design; not yet on hardware.

| File | What it is |
|---|---|
| `gen_gt.tcl` | `omac_gen_versal_gty_quad <ip_dir> ?channels? ?freerun_mhz? ?module_name? ?gt_type?` creates the `gt_quad_base` IP (default module `omac_versal_gty_quad`) and checks the settings below; `omac_versal_ch_of_lane {<ch0> ...}` gives the wrapper's `CH_OF_LANE` |
| `omac_gt_versal_gty_quad.sv` | the wrapper: `IBUFDS_GTE5` for the reference clock, the `gt_quad_base` instance, user clock buffers, the reset controller, bit order, per-lane RX recovery |

## Why gt_quad_base and not a gtwizard

Versal transceivers are configured only through AMD's IP: the GT primitive (`GTYE5_QUAD`) has
hundreds of attributes that only the IP computes. Of the Versal transceiver IPs,
`gt_quad_base` is the one that maps to the UltraScale+ gtwizard role: one quad, every channel's
ports (data, sync header, gearbox, resets, clocks, driver settings) on the IP boundary, no
protocol logic. It can be generated as a plain IP (`.xci`) and instantiated in RTL, so the
wrapper works in a block design (as a module reference or inside one), in a non-project flow
and in simulation, like the UltraScale+ wrappers. The other options were set aside:

| Option | Why not |
|---|---|
| `gt_quad_base` inside a block design with AMD's bridge IP (`gt_bridge_ip`, the "transceiver bridge") | a block-design-only path; the bridge adds AMD's reset logic and its own clocking but nothing the wrapper needs; the design could no longer instantiate the transceiver from RTL |
| `gtwiz_versal` (transceiver wizard subsystem) | a container around `gt_quad_base`, the bridge and the clock buffers; the interface-to-quad mapping of independent single-lane interfaces is harder to script and to check than `gt_quad_base` alone |
| raw mode (no gearbox) + a fabric 64:66 gearbox | not needed: the Versal GTY has the 64B/66B asynchronous gearbox, so `omac_10g` keeps its "one block per `clk` cycle, no gaps" transmit contract ([](interface.md#21-66-bit-block-interface-one-lane)) |

## Usage

```tcl
# in the design's Vivado project (or non-project session)
source <omac>/gt/omac_gt_versal_gty/gen_gt.tcl
set ip [omac_gen_versal_gty_quad [get_property DIRECTORY [current_project]]/ip {0 1} 100]
set_property generate_synth_checkpoint false [get_files [get_property IP_FILE $ip]]  ;# global synthesis
generate_target all [get_files [get_property IP_FILE $ip]]
add_files <omac>/gt/omac_gt_versal_gty/omac_gt_versal_gty_quad.sv
# wrapper parameters: NLANES = 2, CH_OF_LANE = [omac_versal_ch_of_lane {0 1}] (8'h04)
```

`channels` are the **quad channel numbers** (0-3) of the lanes in lane order, lane 0 first (it
is the master: its TX output clock is the shared TX user clock). The quad itself is not in the
IP: Vivado places it from the design's pin constraints (the serial pins or the reference clock
pin), so the same IP serves every quad. Channels of the quad that carry no lane are left
unconnected in the IP (powered down).

## gt_quad_base settings (Vivado 2025.2, gt_quad_base 1.1)

One protocol per lane (`PROT0` = lane 0, ...; `TXn_LANE_SEL` / `RXn_LANE_SEL` of channel n =
the protocol of its lane), each from the preset `GTY-10GBASE-R` and changed where the wrapper
needs it. Read back from the generated IP (`gen_gt.tcl` refuses to continue if a checked value
differs):

| Setting | Value | Note |
|---|---|---|
| preset | `GTY-10GBASE-R` | per protocol |
| line rate TX / RX | 10.3125 Gb/s | |
| reference clock | 156.25 MHz (`TX/RX_REFCLK_FREQUENCY`), source `R0` | one logical reference clock input `GT_REFCLK0` |
| PLL | **RPLL** (TX and RX) | the preset chooses the LCPLL; changed (see below) |
| TX / RX data encoding | `64B66B_ASYNC` (asynchronous gearbox) | `TXSEQUENCE` tied to 0 |
| internal / user data width | **64 / 64** | the preset has 32 / 32 (312.5 MHz); 64 gives one 156.25 MHz user clock per direction |
| TX / RX outclk | `TXPROGDIVCLK` / `RXPROGDIVCLK` at **156.25 MHz** from the RPLL | the user clocks; RX = the recovered clock |
| TX buffer | on (`TX_BUFFER_MODE` 1) | every lane runs from the master lane's TX user clock |
| RX PPM offset | 200 | preset |
| RX equalisation | `AUTO` (port `rx_lpmen`: 0 = DFE, 1 = LPM) | |
| reset | the channel's own sequencer: master resets in sequential mode (`TXRESETMODE` / `RXRESETMODE` 0, the IP's default masks) | |
| register port | APB3 (`apb3clk` = `freerun_clk`) | quad-wide; no per-channel DRP on Versal |

**Why RPLL.** Each half of a Versal GTY quad (HSCLK0: channels 0-1, HSCLK1: channels 2-3) has
an LC-tank PLL and a ring PLL. The 10GBASE-R preset picks the LCPLL; this wrapper uses the RPLL,
which covers 10.3125 Gb/s from 156.25 MHz, and keeps the LCPLL free for another protocol in the
same quad. The choice is fixed in the generator rather than left to the preset. Both lanes of a
half-quad share its RPLL; the wrapper never resets the PLL on a per-lane recovery.

**Bit order.** Unlike the UltraScale+ gearbox, the Versal GTY gearbox sends bit 0 of
`TXDATA` and of `TXHEADER` first, i.e. already in IEEE 802.3 order: the wrapper passes the
blocks through unchanged (`BIT_REVERSE` = 0, the Versal default; the UltraScale+ wrappers
reverse, `BIT_REVERSE` = 1). A data block appears on the GT port `TXHEADER[1:0]` as `2'b10`. A
loop between two lanes of one wrapper cannot detect a wrong bit order (both ends would reverse
alike, and block lock only tests that the two header bits differ); the transceiver-level
simulation therefore also decodes the serial transmit pin independently (the bits from the
transition times, 66-bit alignment, sync header "10" of idle blocks in transmission order,
descrambled idle payload = block type 0x1E sent bit 0 first) and passes only when the line
carries IEEE order. The same check passes on the UltraScale+ GTY wrapper with `BIT_REVERSE` = 1
(whose bit order is confirmed on hardware) and fails on the Versal wrapper with
`BIT_REVERSE` = 1 ([](simulation.md#transceiver-level-simulation-gt-models)).

## Ports and differences from the UltraScale+ wrappers

The parameters `NLANES`, `BIT_REVERSE`, `CH_OF_LANE`, `RST_CYCLES`, `DONE_LOW_CYCLES`,
`DONE_HIGH_CYCLES` and every port of `omac_gt_usp_gty_quad` exist with the same widths and
meaning, with these differences:

| Item | UltraScale+ (`omac_gt_usp_gty_quad`) | Versal (`omac_gt_versal_gty_quad`) |
|---|---|---|
| `BIT_REVERSE` default | 1 (the gearbox sends the MSB first) | **0** (the gearbox sends bit 0 first); a design that sets the parameter explicitly must set it per wrapper |
| `CH_OF_LANE[2l +: 2]` | the gtwizard's channel index of lane l (ascending site order among the generated channels) | the **quad channel number** of lane l (the IP always spans the quad); default `8'hE4` (lane l on channel l) |
| `gt_rx_reset_req[l]` | pulses that channel's `RXPMARESET` | pulses that channel's `RXMSTDATAPATHRESET` (PMA and PCS of the receiver, not the shared PLL); a lane whose receiver does not finish its reset within `DONE_HIGH_CYCLES` retries by itself |
| `qpll_lock` | QPLL0 lock | the RPLL lock of every half-quad in use (name kept) |
| `gt_powergood[l]` | the channel's power good | the quad's power good, on every lane |
| `tx_diffctrl`, `tx_postcursor`, `tx_precursor` | GTY UltraScale+ codes | Versal GTY codes (5 bits each, as the ports); IP default `tx_diffctrl` 25 |
| main cursor | not a port | parameter `TX_MAINCURSOR` (7 bits, default 77, the IP's typical value) |
| `drp_*` | per-channel DRP on `freerun_clk` | **not functional** (Versal has no per-channel DRP): `drp_do` = 0, `drp_rdy` answers every `drp_en` one cycle later; ports kept for compatibility |
| register access | DRP | new ports `apb_paddr[15:0]`, `apb_psel`, `apb_penable`, `apb_pwrite`, `apb_pwdata[31:0]`, `apb_prdata[31:0]`, `apb_pready`, `apb_pslverr`: the quad's APB3 port on `freerun_clk` (tie `apb_psel` and `apb_penable` to 0 when unused) |
| user clocks | `TXUSRCLK` 312.5 MHz + `TXUSRCLK2` 156.25 MHz (two `BUFG_GT` per direction) | one 156.25 MHz user clock per direction (Versal channels have no USRCLK2): one `BUFG_GT` for TX, one per RX lane |
| `refclk_mon` | `IBUFDS_GTE4` ODIV2 / 8 | `IBUFDS_GTE5` ODIV2 / 8 (19.53 MHz at 156.25 MHz) |
| parameter `SIM_DEVICE` | - | the `BUFG_GT` architecture (`VERSAL_AI_CORE` for VC1902 parts; set it for other Versal families) |

## Resets and handshake (software view)

The same rules as on UltraScale+ ([](gt_usp_gth.md#resets-and-handshake-software-view)): one
input for the design (`reset_all`), the rest is a handshake with the omac IP.

| Port | Software rule |
|---|---|
| `freerun_clk` | the reset controller's and the APB3 clock (100 MHz in the generator's default): a clock independent of the transceiver that runs before and during `reset_all` (on Versal a CIPS `pl0_ref_clk`) |
| `reset_all` | hold it from power-up until the reference clock is stable at 156.25 MHz (a programmable clock generator programmed first), then release it once. While it is held, every channel's `TXMSTRESET` and `RXMSTRESET` are asserted and `tx_usrclk2` does not run |
| `gt_tx_ready` | after `reset_all` and the quad's power good: the master resets are released, the TX user clock starts, `TXUSERRDY` follows 32 cycles later and the channels report `TXMSTRESETDONE`. If `TXMSTRESETDONE` does not come within `DONE_HIGH_CYCLES` the controller starts over |
| `gt_rx_ready[l]` | the same per lane for the receiver (`RXMSTRESETDONE` of the lane's channel, its RX user clock running); low during every per-lane recovery |

The reset sequence of each channel (PLL, PMA, programmable dividers, PCS, in that order) runs
inside the transceiver; the controller only starts it, provides `USERRDY` once the user clock
runs and waits for the done flag.

## Clocking and SyncE

* **TX:** the master lane's `TXOUTCLK` (`TXPROGDIVCLK` = RPLL / 66 = the reference clock
  frequency) through one `BUFG_GT` is `tx_usrclk2`, the `clk` of every `omac_10g` and the user
  clock of every lane (TX buffer on). Every lane transmits from the quad's RPLL, i.e. from the
  reference clock alone: when that clock comes from a SyncE DPLL every port transmits a
  traceable line clock, nothing in the fabric re-times the transmit path.
* **RX:** each lane's `RXOUTCLK` (`RXPROGDIVCLK`, the recovered clock) through its own
  `BUFG_GT` is `rx_usrclk2[l]` = the omac `gt_rx_clk` of that lane, for SyncE frequency
  monitoring.
* **Time base:** as on UltraScale+, `tx_usrclk2` is a fixed multiple of the reference clock and
  can be the design's time-of-day clock; it stops while `reset_all` is held.
* **Reference clock input:** the IP has one logical input (`GT_REFCLK0`); the `IBUFDS_GTE5` sits
  on the pin of the design's constraints, `MGTREFCLK0` or `MGTREFCLK1` of the quad, and Vivado
  routes it to the PLL without further constraints (placed and routed with `MGTREFCLK1` in the
  VCK190 FMCP1 design; `MGTREFCLK0` is not yet part of a placed design). A reference clock of
  another quad is not supported by this wrapper.

## Clock constraints

* **Reference clock:** `create_clock -period 6.400` on the reference clock pin and its
  `PACKAGE_PIN`; the serial pins' package pins select the quad.
* **Transceiver output clocks:** Vivado creates them itself from the quad's configuration:
  `ch<n>_txoutclk` and `ch<n>_rxoutclk` (156.25 MHz) on the `CH<n>_TXOUTCLK` /
  `CH<n>_RXOUTCLK` pins of the used channels (`<n>` = the quad channel; only the master lane's
  `TXOUTCLK` drives logic). The `BUFG_GT`s propagate them to `tx_usrclk2` and `rx_usrclk2[l]`;
  constrain the crossings by these names (or through the pins, as on UltraScale+). A
  `create_clock` on those pins only replaces the derived clock (warning Timing 38-3).
* **Clock crossings:** as on UltraScale+ ([](gt_usp_gth.md#clock-constraints)): the TX user
  clock and the recovered clocks are asynchronous; bound the crossings with
  `set_max_delay -datapath_only` of one `clk` period or with asynchronous clock groups.

## Board placement

A design determines, for its board and connector: the quad of the lanes (from the serial pins'
package pins, for Opsero FMC cards from the
[FPGA Board Repository](https://boards.fpgadeveloper.com)), each lane's quad channel number in
lane order (the generator's `channels`), the quad's reference clock pin (`MGTREFCLK0` or
`MGTREFCLK1`, with its 156.25 MHz source that must be stable before `reset_all` is released) and
the lane polarity where the board swaps P and N (`tx_polarity` / `rx_polarity`). The lanes'
channels and the reference clock must be in one quad.

Example, two FMC lanes on the AMD VCK190 FMCP1 connector: DP0 = channel 0 and DP1 = channel 1 of
the FMCP1 quad (bank 201, `GTY_QUAD_X1Y1`), GBTCLK0 = `MGTREFCLK1` of the same quad:
`channels` = `{0 1}`, `CH_OF_LANE` = `8'h04`.

## GTYP

Versal Premium, AI Edge Gen 2 and HBM devices have GTYP quads, configured through the same
`gt_quad_base` IP. `omac_gen_versal_gty_quad ... GTYP` generates the IP from the
`GTYP-10GBASE-R` preset with the same changes and passes the same checks (RPLL,
`64B66B_ASYNC`, 64-bit widths, 156.25 MHz output clocks; tried on xcvp1202). The wrapper does
not take it yet: the GTYP flavour of the IP has a different set of reserved and debug ports
(for example no `ch<n>_cfokovrd*` / `tstin` / `altclk`, additional `ch<n>_dfehold`,
`*dapireset*`, `*qpi*`, 32-bit `gpi`), and the wrapper connects every input of the IP
explicitly. A GTYP variant of the instance (its own tie-off list, selected by a parameter) is
the remaining work ([](roadmap.md)).

## Proving the wrapper on hardware

What a hardware proof needs (none of it is specific to the wrapper): a Versal board with a quad
that carries 10G-capable SFP+ / SFP28 cages or an FMC with them (for example a quad SFP28 FMC on
the VCK190 FMCP1 connector), a 156.25 MHz reference clock on that quad (on a programmable clock
generator: program it before releasing `reset_all`; `refclk_mon` shows it), the cage sideband
(TX_DISABLE low, module presence) and a 10GBASE-R partner with auto-negotiation and FEC off (a
NIC port over a DAC or optics, or two cages looped with a DAC). Checks: `gt_tx_ready`,
`gt_rx_ready`, block lock and link up on every lane, frames both ways without FCS or block
errors, link recovery after a cable pull on one lane without disturbing the others (the per-lane
`RXMSTDATAPATHRESET`), and the transmit frequency following the reference clock.
